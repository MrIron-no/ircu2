# P11 Server-to-Server Protocol

P11 is the eleventh revision of the ircu2 server-to-server (S2S) protocol. It
is not a separate protocol: it is P10 with a set of extensions that are
negotiated per link. A server speaks full P10 to a P10 peer and uses the P11
form of a message only on a link where both ends have agreed on protocol 11.

This document specifies what P11 defines or changes relative to P10. For the
base protocol — wire format, numerics, the token table, the net burst, and
every message P11 leaves unchanged — see [p10.md](p10.md). The original
historical P10 specification is preserved at [history/p10.html](history/p10.html).

## 1. Versioning

- Base version: `u2.11.0.0`.
- Major protocol version: `11` (`MAJOR_PROTOCOL`, derived from the `AC_INIT`
  version in `configure.ac`).
- Minimum protocol accepted at link time: `10` (`MINOR_PROTOCOL` in
  `include/ircd.h`). A peer announcing a lower version is refused during
  registration.

The major version is the number carried in the `SERVER` handshake and stored
per link. The minor floor governs which peers may link at all.

## 2. Negotiation

A server announces its protocol in the `SERVER` message as a `P` or `J` token
followed by the version — `P11` or `J11` for a P11 server (`J` while the
server is still bursting, `P` once its burst is complete; see [p10.md](p10.md)
§4).

The announced number is clamped to the receiver's own major version, so the
protocol stored for a link is the **minimum** of the two ends' versions. That
stored value, reached as `Protocol(link)`, is the link's negotiated protocol.
A link between a P11 and a P10 server negotiates to 10, and the P11 server
uses the P10 form of every message on it.

## 3. Per-link gating

Every P11 extension is selected per link by the negotiated protocol, not by a
network-wide configuration flag. A P11 form is emitted to a peer, and expected
from a peer, only when that link is at protocol 11 or above:

```
if Protocol(link) >= 11:  use the P11 form
else:                     use the P10 form
```

This mirrors the older `Protocol(x) < 10` guards that gated legacy behaviour.
No network-wide flag day is required: each link independently uses the highest
protocol both ends understand, and a mixed P10/P11 network converges without
coordinated configuration.

## 4. Server prefixes

A server prefix is always a numeric: a numeric nick (client) or a numeric
server token. The P10-era textual (`:nick`/`:server`) prefix form is not
accepted. This applies on every link; it is a consequence of protocol 9 no
longer being supported (§1), since only a P9 peer emitted textual prefixes.

## 5. MODE (`M`) — channel timestamp

The channel `MODE` message carries a trailing channel creation timestamp:

```
<numnick> M <#channel> <modes> [<args>] <channel-ts>
```

On a P11 link the `<channel-ts>` is a **mandatory, positional** final
parameter, validated as an all-digit decimal value. A set-mode from a P11
peer that carries no valid timestamp — either a non-numeric final argument
or no trailing timestamp at all — is a protocol violation, and the mode is
**dropped**: neither applied nor propagated. Because every server appends
its own creation time when it propagates a MODE, an ircu-sourced mode always
carries a timestamp; a TS-less MODE over a P11 link therefore indicates a
non-compliant directly-connected peer, and dropping it keeps all ircu servers
consistent.

On a P10 link the timestamp is instead detected by the legacy heuristic — the
final argument, taken as the timestamp if it begins with a digit — and a
mode with no timestamp is accepted (the receiver adds one on propagation).
That heuristic can misread an unconsumed mode argument (for example a numeric
nick beginning with a digit, which an unknown mode letter did not consume) as
the timestamp; the P11 form removes the ambiguity.

The timestamp itself is compared to the local creation time as in P10: an
earlier timestamp replaces the local one, a later timestamp from a
non-bursting peer indicates a desync and bounces the mode.

## 6. INVITE (`I`) — target and op notification

### Target addressing

On a P11 link the S2S `INVITE` addresses its target user by numnick, resolved
with a numnick lookup, consistent with every other user-directed command
(`KILL`, `KICK`, `PRIVMSG`, and so on):

```
<numnick> I <target-numnick> <#channel> [<channel-ts>]
```

On a P10 link the target is the target's nickname, resolved by name. Because
an invitee may be on a P10 server, a P11 server that forwards an invite toward
a P10 link renders the target as a nickname on that hop.

Addressing by numnick removes the failure mode of the nickname form, in which
an invite crossing a nick change could be dropped or delivered to a different
user who now holds that nickname.

### Operator notification

When a user is invited, channel operators with the `invite-notify` client
capability are sent the invite. The invite is propagated across the network
the way a channel message is: one copy per onward server link that leads to a
channel operator or to the invitee, never back down the link it arrived on.
Each receiving server relays it onward the same way, notifies its own local
operators, and — if it hosts the invitee — delivers the invite. There is thus
a single propagation: every operator, and the invitee, is reached exactly
once, with no reflection or fan-out. The propagated invite carries a numnick
target, so it travels only over P11 links; a P10 invitee's server, which does
not take part, still receives a direct nickname-form invite for delivery.

There is no separate feature toggle for operator notification and no numeric
form of it; the earlier `ANNOUNCE_INVITES` feature and its `RPL_ISSUEDINVITE`
(345) numeric are not part of P11.

## 7. KILL (`D`) — path and reason

On a P11 link the `KILL` message carries the kill path and the reason as two
separate positional parameters:

```
<source> D <target-numnick> <path> :<reason>
```

On a P10 link the two share the single trailing parameter, separated by a
space, and the receiver splits on the first space:

```
<source> D <target-numnick> :<path> <reason>
```

Separating the parameters removes the P10 ambiguity in which a path long
enough to fill the message truncates the reason, or a reason with no embedded
space cannot be told apart from a continuation of the path. A relaying server
folds its own hop onto the path and caps the accumulated path at a fixed
length (300 characters); on a P11 link the split then guarantees the reason
survives intact regardless of how long the path has grown, whereas on a P10
link a sufficiently long path can still crowd the shared parameter.

A P11 server renders the appropriate form per destination link: a kill it
forwards toward a P10 peer is packed into the combined trailing parameter, and
one toward a P11 peer keeps the path and reason split. The target is addressed
by numnick on both forms.

## 8. User modes

The user-mode string carried in the `NICK` introduction and in server burst
uses the P11 form on a P11 link and the P10 form on a P10 link. A server
renders the appropriate form per destination link.

## 9. Labeled responses

The IRCv3 labeled-response mechanism (`@label=` request tags and `@batch=`
grouped replies) is federated across server links only on P11 links. On a P11
link an incoming request label is captured, and a pending capture is handed
onward with its `@label=` tag; the labeled reply is returned in a `BATCH`.

A P10 link carries neither `@label=` nor `@batch=`. A request whose reply must
cross a P10 hop cannot be labeled, so it degrades to an ordinary unlabeled
reply with no `ACK` — the fallback the labeled-response specification sanctions
for a response a server cannot label. A forwarding server hands its capture off
on any S2S forward, so it never emits a spurious `ACK` for a command that does
produce a reply.

## 10. Compatibility

- A P11 server is a full P10 server to every P10 peer: no P10 behaviour is
  removed or altered on a P10 link.
- Enabling P11 on one server affects only that server's P11 links; no
  coordinated, network-wide change is required.
- Protocol 9 is not supported. A peer announcing protocol 9 is refused at link
  time, and the TS8 compatibility behaviour it required is not present.
